# Draft: upstream report on server shutdown and run cancellation for the Maltego SDK

Not yet filed. Review and send to Maltego (SDK support or the `maltego-transforms` issue tracker).
Kept in the repo because `server/project.py` patches `uvicorn.Config` to work around the first
point, and `transformatron stop` explains the other stalls in its kill message. If these are fixed
upstream, the patch can go and the message will rarely be seen.

---

## Title

Server shutdown can stall for 30s, 60s or indefinitely, and cancelling a run has no effect until
the runner loop wakes

## Versions

- `maltego-transforms` 1.3.0 (also seen on 1.0.1)
- `uvicorn` 0.35.0
- Python 3.14, macOS

## Summary

SIGTERM to a server started with `run_server` can take far longer than expected to finish:

| What is open when SIGTERM arrives | Time to exit |
|---|---|
| Nothing | under 1s |
| An idle HTTPS keep-alive client (for example Maltego Desktop's connection pool) | 30s |
| A TCP connection that has not finished its TLS handshake | 60s |
| A transform blocking its runner thread | until the transform returns |

Process managers usually SIGKILL after a grace period (Docker and systemd default to 10s and
90s, and our tooling uses 10s). A kill at that point looks like a crash. Three changes in the SDK
would bound these waits. A fourth issue, also in this area, makes run cancellation late.

## 1. Expose uvicorn's `timeout_graceful_shutdown`, with a finite default

### Cause

`MaltegoServer.__get_config` builds the `uvicorn.Config` itself
(`maltego/server/__init__.py:373-384` for HTTPS, `:385-394` for HTTP). It sets no
`timeout_graceful_shutdown`, so uvicorn uses its default of `None` (`uvicorn/config.py:216`).
`ServerHTTPSettings` (`maltego/model/server.py:269`) has no field for it, and uvicorn reads no
environment variable for it. The setting cannot be changed without patching a third-party class.

With `None`, `uvicorn.Server.shutdown` waits without a limit (`uvicorn/server.py:279-282`):

- **Idle TLS keep-alive peer.** uvicorn asks each connection to close and then logs
  `Waiting for connections to close. (CTRL+C to force quit)` (`uvicorn/server.py:298`). Over
  TLS, the close sends `close_notify` and waits for the peer's reply, or for
  `asyncio.constants.SSL_SHUTDOWN_TIMEOUT` (30.0s). A pooled client that is not reading never
  replies.
- **Pending TLS handshake.** `_wait_tasks_to_complete` ends with `await server.wait_closed()`
  (`uvicorn/server.py:311`). Since Python 3.12.1 that waits for every accepted transport to drop
  (`asyncio/base_events.py:390`), including one still in its TLS handshake. Such a transport
  lasts until `SSL_HANDSHAKE_TIMEOUT` (60.0s). uvicorn does not track it as a connection, so
  nothing is logged after `Shutting down`.

### Reproduction

Start any server with HTTPS, for example a project generated by `maltego-transforms start server`
and run with `python project.py` on port 3000. Then, from a second shell, hold one connection
open:

```python
import socket
import ssl
import time

raw = socket.create_connection(("127.0.0.1", 3000))
ctx = ssl.create_default_context()
ctx.check_hostname = False
ctx.verify_mode = ssl.CERT_NONE
conn = ctx.wrap_socket(raw, server_hostname="127.0.0.1")
conn.sendall(b"GET /api/v3/status HTTP/1.1\r\nHost: 127.0.0.1\r\nConnection: keep-alive\r\n\r\n")
conn.recv(65536)
time.sleep(120)  # an idle pooled connection: neither reads nor closes
```

Send `kill -TERM <server pid>` and time how long the process takes to exit. For the handshake
case, replace the script with `nc 127.0.0.1 3000`, which connects and sends nothing.

Observed on 1.3.0:

```
idle TLS keep-alive peer:   exited 30.1s after SIGTERM
    12:40:16 uvicorn | Shutting down
    12:40:16 uvicorn | Waiting for connections to close. (CTRL+C to force quit)
    12:40:46 uvicorn | Waiting for application shutdown.
    12:40:46 uvicorn | Application shutdown complete.
pending TLS handshake:      exited 59.0s after SIGTERM
    12:40:48 uvicorn | Shutting down
    12:41:47 uvicorn | Waiting for application shutdown.
    12:41:47 uvicorn | Application shutdown complete.
```

Over plain HTTP, the same idle keep-alive peer exits in about 0.2s, because a plain socket close
is immediate.

### Workaround we ship

Before calling `run_server`, wrap `uvicorn.Config.__init__` to call
`kwargs.setdefault("timeout_graceful_shutdown", 3)`. This works only because `__get_config`
passes every argument by keyword. With it, both cases above exit 3.2s after SIGTERM, and the
log shows `Cancel 0 running task(s), timeout graceful shutdown exceeded` followed by a clean
lifespan shutdown.

### Suggested fix

Add a `timeout_graceful_shutdown: Optional[int]` field to `ServerHTTPSettings`, so it can be set
from `MALTEGO_SERVER_TIMEOUT_GRACEFUL_SHUTDOWN`. Give it a finite default (a few seconds) and pass
it to both `uvicorn.Config(...)` calls in `__get_config`. Any default well under common
orchestrator grace periods avoids the SIGKILL.

## 2. Bound the runner shutdown in the lifespan

### Cause

The lifespan's shutdown branch calls `self.runner.shutdown()` synchronously on the uvicorn event
loop (`maltego/server/__init__.py:253`). For `ThreadedTransformRunner` that is
`shutdown(wait=True, cancel_futures=False)` (`maltego/runner/__init__.py:544-549`). It asks each
worker loop to stop and then `executor.shutdown(wait=True)` joins the worker threads.

Each worker loop's own drain is bounded at 2s (`_CANCELLATION_DRAIN_TIMEOUT_SECONDS`,
`maltego/runner/__init__.py:383`, used by `_drain_cancelled_tasks` at `:427`). A transform
that blocks its thread cannot be cancelled, though, so the join waits for as long as the
transform runs. Examples are a sync HTTP client, `time.sleep`, or CPU-bound work. Sync `def`
transforms run inline on the worker loop (`__add_sync_results`,
`maltego/model/transform/__init__.py:683`), so they hit the same path.
`timeout_graceful_shutdown` does not help, because it bounds only the connection phase.

### Reproduction

```python
import time

from maltego.entities import Phrase
from maltego.model.context import MaltegoContext
from maltego.server import register_transform


@register_transform(display_name="slow probe", transform_set="probe")
async def slow_probe(input_entity: Phrase, context: MaltegoContext) -> list[Phrase]:
    time.sleep(25)  # stands in for any blocking call
    return [Phrase(value="done")]
```

Run the transform, and send SIGTERM to the server 4s later.

Observed on 1.3.0: the process exits 21.2s after SIGTERM, when the sleep ends. The log shows
`Waiting for application shutdown.` at SIGTERM (12:41:52) and `Application shutdown complete.`
only when the transform returns (12:42:13). The result is the same, 21.2s, with
`timeout_graceful_shutdown=3`. A `faulthandler` dump during the stall shows the main thread in
`threading.join`, called from `concurrent/futures/thread.py` `shutdown`, called from
`maltego/runner/__init__.py:549`, called from the lifespan at `maltego/server/__init__.py:253`.

### Suggested fix

Do not block the event loop on the join. Either call
`self.runner.shutdown(wait=False, cancel_futures=True)` from the lifespan, or run the blocking
shutdown in a thread and wait for it with a timeout:

```python
await asyncio.wait_for(asyncio.to_thread(self.runner.shutdown), timeout=...)
```

uvicorn restores the original signal handlers and re-raises the captured signal once `serve()`
finishes (`uvicorn/server.py:321-331`). For SIGTERM that means the default action, so the
process exits even if a worker thread is still stuck. For SIGINT it means `KeyboardInterrupt`,
and interpreter exit then joins the executor's non-daemon threads, so `wait=False` alone does
not bound a Ctrl+C. Whichever route is taken, a log line naming the transform still running
would make the stall diagnosable.

## 3. Make run cancellation thread-safe

### Cause

`DELETE …/transforms/{transform_id}/run/{run_id}` (`delete_transform_run`,
`maltego/server/v3/__init__.py:992`) and `POST …/run/{run_id}/cancel` (`cancel_transform_run`,
`:1100`) call `transform_runner.cancel(run_id)` (`:1032`, `:1151`). That looks up the run and
calls `TransformExecutionContext.cancel()` (`maltego/runner/__init__.py:203-210`), which calls
`self.task.cancel()` and the same on the before- and after-transform tasks
(`maltego/runner/transform_execution_context.py:331-341`).

These run on the uvicorn thread, but the tasks belong to a runner thread's event loop
(`self.task` is created at `transform_execution_context.py:390`, and the loop runs at
`maltego/runner/__init__.py:484`). `Task.cancel()` is not thread-safe. It schedules the
cancellation with `loop.call_soon`, which does not wake that loop's selector. So the
cancellation takes effect only when something else wakes the worker loop, such as the next
run's `call_soon_threadsafe` or the shutdown's `_close`. Until then the transform keeps its
upstream request, and any rate-limit slot it holds.

### Reproduction

Standalone, with no server, and mirroring the runner's thread layout:

```python
import asyncio
import threading
import time

# The runner's worker: an event loop on its own thread (runner/__init__.py:477-484).
loop = asyncio.new_event_loop()
threading.Thread(target=loop.run_forever, daemon=True).start()

started = time.monotonic()


async def transform() -> None:
    try:
        await asyncio.sleep(3600)  # an awaiting transform, e.g. a slow upstream request
    except asyncio.CancelledError:
        print(f"transform saw the cancel {time.monotonic() - started:.1f}s after it was requested")
        raise


tasks: list[asyncio.Task] = []
loop.call_soon_threadsafe(lambda: tasks.append(loop.create_task(transform())))
time.sleep(0.2)

# What TransformExecutionContext.cancel() does from the uvicorn thread
# (transform_execution_context.py:337-338).
started = time.monotonic()
tasks[0].cancel()
time.sleep(5)
print(f"after 5s: task done = {tasks[0].done()}")

# Anything else that wakes the worker loop, e.g. the next run being scheduled.
loop.call_soon_threadsafe(lambda: None)
time.sleep(0.2)
print(f"after waking the loop: task done = {tasks[0].done()}")

# The thread-safe form takes effect at once.
tasks.clear()
loop.call_soon_threadsafe(lambda: tasks.append(loop.create_task(transform())))
time.sleep(0.2)
started = time.monotonic()
loop.call_soon_threadsafe(tasks[0].cancel)
time.sleep(0.2)
print(f"call_soon_threadsafe(task.cancel): task done = {tasks[0].done()}")
```

Observed:

```
after 5s: task done = False
transform saw the cancel 5.0s after it was requested
after waking the loop: task done = True
transform saw the cancel 0.0s after it was requested
call_soon_threadsafe(task.cancel): task done = True
```

End to end, on a live server: a transform that awaits `asyncio.sleep` was run with a 3s client
timeout. The client posted `/cancel` at 11:15:07. The run's `finished with state CANCELED`
appeared at 11:15:23, at the moment an unrelated run woke the worker loop.

### Suggested fix

In `TransformExecutionContext.cancel()`, cancel through the task's own loop:

```python
for task in (self.before_transform_task, self.task, self.after_transform_task):
    if task is not None:
        task.get_loop().call_soon_threadsafe(task.cancel)
```

`set_end_time()` and any state change that follows should then happen on that loop too, or
under a lock, since they are read from the uvicorn thread.

## Impact

- Orchestrators and wrappers that SIGKILL after a grace period kill healthy servers whenever a
  desktop client is connected over HTTPS. This is the normal deployment, because Maltego
  Desktop refuses plain HTTP.
- One blocking transform holds up every restart, with no log line pointing at it.
- A cancelled or timed-out run keeps consuming upstream quota until the worker loop happens to
  wake.
